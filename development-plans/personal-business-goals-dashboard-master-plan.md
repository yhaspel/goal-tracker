# Family Kanban Board — Master Development Plan

**Status:** Revised and split into seven implementation-ready stage plans  
**Planning baseline:** 2026-09-12  
**Document language:** English. The product UI will support English, Hebrew, and Russian.

## 1. Product and scope

Build one small, private Kanban board for one household or working group with **up to seven active users, including its owner**. Each person signs in with an email address and password. Members can create and edit task cards, drag them within or between columns, and assign a card to one active member. All active members can see and edit the same board. This revision supersedes the previous multi-goal dashboard design.

The initial board has **To Do**, **In Progress**, and **Done** columns. Their built-in labels are translated until renamed; user-supplied names remain as entered. The owner can add, rename, reorder, and remove empty columns, but at least one column must remain; every member can add, edit, move, assign, and delete cards. A card has only a title, optional description, optional assignee, column, and position. Show a confirmation before deleting. Keep the first release limited to one group and one board. Do not build goals, goal progress, private boards, subtasks, labels, due dates, attachments, notifications, live collaboration sockets, or AI-generated plans. The saved prompt in `prompts/goal-settings-prompt.md` remains reference material and is not an integration requirement.

Use invitation-only registration. The owner issues a single-use invitation for a specified email and shares its code outside the app. Email is an account identifier; the app sends **no email**, does not verify email ownership, and exposes no email-based password reset. The invited person chooses a password and must save and confirm a one-time recovery phrase before the account becomes active. If the phrase is lost, the person contacts the owner for a verified, manual database reset.

## 2. Technology and hosting decision

| Layer | Decision |
| --- | --- |
| UI | React, TypeScript, Vite, and `@dnd-kit/react` for pointer, touch, and keyboard dragging ([sensor documentation](https://dndkit.com/react/guides/sensors/)) |
| API | TypeScript in the same Cloudflare Worker deployment; JSON endpoints under `/api/v1/` |
| Persistence | One **SQLite-backed Durable Object**, selected by a fixed household name, for users, sessions, invitations, columns, cards, and recovery state |
| Hosting | **Cloudflare Workers Free only**: Worker Static Assets for the UI, Worker code for the API, and the bound Durable Object for SQL storage |
| Address | The included `workers.dev` HTTPS hostname; a purchased domain is unnecessary |

This is one hosting provider, one application deployment, and no separately hosted database. Configure `assets.run_worker_first: true` and omit the automatic SPA fallback. The Worker dispatches `/api` and `/api/*` before assets, returns JSON/404 for unknown API routes, and explicitly serves `index.html` only for known client-side navigation paths. Missing assets and unknown paths return 404. This routes static requests through the Worker and counts them against its Free request quota; measure that usage during the trial. The front Worker should only route and validate basic request shape; the Durable Object owns authenticated operations and password hashing. Cloudflare documents [Worker-first asset routing](https://developers.cloudflare.com/workers/static-assets/binding/), [SQLite-backed Durable Objects on Free](https://developers.cloudflare.com/durable-objects/platform/limits/), and the [included `workers.dev` route](https://developers.cloudflare.com/workers/configuration/routing/).

As checked on the planning date, Workers Free permits 100,000 Worker requests/day; SQLite-backed Durable Objects on Free include 100,000 requests/day, 13,000 GB-seconds/day, 5 million SQL rows read/day, 100,000 rows written/day, and 5 GB stored across the account, with a **1 GB per-object Free ceiling** stated in Cloudflare's limits FAQ. A Durable Object has a default 30-second CPU limit per request, while the front Worker Free limit is much shorter; keep the expensive password operation inside the object. Free-tier excess operations fail rather than silently converting to paid usage. These quotas are ample for a seven-person text-only board but are not an uptime guarantee. Check current terms before implementation and release. [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) · [Durable Object pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/) · [Durable Object limits](https://developers.cloudflare.com/durable-objects/platform/limits/)

Use the supported `node:crypto` **scrypt** implementation inside the Durable Object with a unique random salt and a versioned parameter record. Start with OWASP's memory-conscious setting `N=2^14, r=8, p=5`, then benchmark hashing and verification in the actual Free deployment before building authentication. Do not weaken the work factor to fit a runtime limit. This avoids WebCrypto PBKDF2's reported 100,000-iteration ceiling in Workers. If the native scrypt call or its benchmark fails, stop at Stage 1 and reassess the platform before implementing accounts. [Workers `node:crypto` support](https://developers.cloudflare.com/workers/runtime-apis/nodejs/crypto/) · [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) · [PBKDF2 runtime issue](https://github.com/cloudflare/workerd/issues/1346)

Other single-provider options were considered. Netlify Database's compute uses credits from the same 300-credit Free pool as deploys and traffic, making frequent family use harder to budget. PythonAnywhere Free requires periodic web-app renewal. Deno Deploy Free can host an app and KV together, but its new KV integration lacks manual backups and its full Free quotas require card verification. The Cloudflare choice keeps SQL, the app, and a basic HTTPS address under one Free account. [Netlify Database billing](https://docs.netlify.com/build/data-and-storage/netlify-database/billing-and-usage/) · [PythonAnywhere Free features](https://help.pythonanywhere.com/pages/FreeAccountsFeatures/) · [Deno Deploy changelog](https://docs.deno.com/deploy/changelog/)

## 3. Data model and API behavior

Store schema-versioned SQL tables for `users`, `invitations`, `pending_registrations`, `sessions`, `recovery_credentials`, `operator_reset_tokens`, `rate_limits`, `columns`, `cards`, and `board_state`. Use stable IDs, UTC timestamps, unique normalized email, foreign keys or equivalent validated references, and indexes for card column/position and live sessions. Keep all application records in the named Durable Object so there is no cross-database transaction. Never persist a plaintext password, invitation code, recovery phrase, session token, or operator token. Seed the three default columns once in an idempotent schema migration.

Expose a small versioned JSON API for bootstrap/session, invitations and members, registration, login/logout, recovery, board read, column management, and card CRUD/move. Validate length and type server-side: title 1–200 characters, description at most 4,000 characters, column names 1–80 characters. Return consistent errors and appropriate `401`, `403`, `404`, `409`, and `429` statuses. Every board endpoint requires a live session; only the owner may change members or columns. Assignments must reference an active user in this group. Deactivation revokes sessions, removes the user from assignment choices, and clears that user's current card assignments; historical card text and creator metadata remain. The owner cannot deactivate their own account in this release.

Persist each column's order and each card's position. A board mutation checks the client's `boardRevision`, validates the target column/assignee, updates affected positions and the card, and increments the revision in **one Durable Object SQLite transaction**. A stale client receives `409` plus the current revision; the UI reloads the board, preserves unsaved card-form values for review and retry, and shows that an attempted move was not saved. This prevents a concurrent drag or edit from silently overwriting another member's work. No socket service is needed: refetch after mutations, when the tab regains focus, and periodically only while the board is visible. Keep pagination or bounded reads available if the board grows.

## 4. Accounts, phrase recovery, and security

1. **Owner bootstrap:** While no owner exists, a one-time bootstrap route requires a high-entropy secret configured in Cloudflare; owner creation and bootstrap consumption are atomic. Once the owner exists, the route is permanently closed by database state. Keep the secret out of source control and remove it from deployment configuration after use.
2. **Invitations and seats:** The owner creates an invitation bound to a normalized email; its code has at least 128 bits of randomness, is stored as a digest, expires after seven days, and can be consumed once. Registration confirms the code, password, and saved phrase. Enforce the seven-active-user limit in the same SQL transaction that activates the account, including simultaneous acceptance attempts. Expired or revoked invitations and duplicate emails cannot activate accounts.
3. **Passwords and sessions:** Hash passwords with the benchmarked scrypt parameters and per-user salts. Enforce a reasonable length and reject common passwords. Use random opaque session tokens, store only their digests, set a `Secure; HttpOnly; SameSite=Lax; Path=/` cookie, and rotate/revoke sessions on login, logout, password change, deactivation, and recovery. Do not store tokens in `localStorage`. Require an exact same-origin `Origin` check and a session-bound CSRF header on mutations. Add persistent per-account and per-IP rate limits and generic login/recovery errors; log security events without secrets.
4. **Recovery phrase:** Generate 12 independent words from a pinned 2,048-word list using a cryptographic random generator. Show the phrase once; require the person to re-enter it before activation. Normalize only case and whitespace for verification. Store a keyed digest with the digest key as a Cloudflare secret. A user with the phrase may reset the password; completing the reset issues a fresh phrase, consumes the old phrase, and revokes all sessions atomically. An interrupted reset leaves the original credentials valid. There is no email-reset route or mail integration.
5. **Lost phrase:** The owner verifies the person through a known offline channel. A trusted local token generator creates a high-entropy, short-lived reset token and its digest; the operator inserts the digest, user ID, and expiry into the `operator_reset_tokens` SQL table through Cloudflare's access-controlled Durable Object Data Studio. The user redeems the one-time token in the app and sets a new password and new phrase; all sessions are revoked. Keep exact SQL, identity-check steps, and audit instructions in the runbook. Never reveal the old password or phrase. [Durable Object Data Studio](https://developers.cloudflare.com/durable-objects/observability/data-studio/)

Every API authorization rule is enforced in the Durable Object, not merely in the UI. Add secure response headers, content security policy appropriate to the final bundle, HTTPS-only operation, request-body limits, and escaping of user-authored card content. Credentials and recovery material must never appear in logs or analytics.

## 5. Three languages, direction, and usable drag-and-drop

Ship complete UI dictionaries for `en`, `he`, and `ru`, with English fallback for a missing key during development and a build check that fails on missing release translations. Store each user's language preference; guests use a non-sensitive language cookie or browser preference. Switching languages updates the screen immediately and persists the preference after sign-in. Set `<html lang>` and `<html dir>` to `he`/`rtl` or `en|ru`/`ltr`; use CSS logical properties and mirror directional icons. Render user-authored card text with `dir="auto"`, while email, codes, and recovery words remain LTR. Translate validation, auth/recovery, board controls, empty states, and accessibility labels, not just navigation. Format dates and numbers by locale if displayed.

Support pointer and touch dragging, keyboard drag/reorder, and explicit **Move to column**, **Move up**, and **Move down** controls. Those controls provide a reliable fallback on mobile and for assistive technology. Announce successful and rejected moves, preserve focus after dialogs and moves, and check contrast and visible focus. On small screens, columns may scroll horizontally, but all actions must remain reachable. Acceptance testing covers mixed Hebrew/English card text and the entire registration/recovery flow in all three languages.

## 6. Backups, limits, and operation

Cloudflare's SQLite-backed Durable Objects expose a **30-day point-in-time recovery API**, but this is not a substitute for independent copies. Build an operator-only, authenticated export of schema-versioned application data (excluding live sessions and rate-limit state). A trusted local script downloads and encrypts one backup every week, retains four weekly and three monthly copies, and keeps its encryption key separately. Securely escrow the recovery-digest secret and other required application secrets **separately** from the data backup; a restore to a new account must restore those secrets or explicitly re-enroll affected credentials. Build an import into an **empty isolated object in a separate Wrangler environment/namespace** for restore drills; its operator route selects only that environment's fixed object, never the production one. Production replacement requires a documented maintenance procedure, validation, and an explicit operator action. Run a monthly restore drill. Verify export and import sizes and CPU usage on the actual Free runtime. Do not expose backup import/export in the member UI. [SQLite storage and point-in-time recovery](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)

Use local development with Wrangler and an isolated local Durable Object. Deploy the single Worker with Static Assets and the SQLite Durable Object binding through Wrangler to the Free account. Pin dependency and compatibility dates. Track Worker requests, Durable Object requests/duration, SQL rows, and storage during a realistic seven-user trial; set a simple usage review cadence in the runbook. When a Free quota is exceeded, show a useful error where possible and wait for reset or reduce usage. Treat the free `workers.dev` deployment as a best-effort personal project, with no availability SLA. Recheck pricing, limits, and API behavior at Stage 1 and before release.

## 7. Implementation stages

The [development-plan index](README.md) links **one detailed English subplan per numbered stage**. Each subplan contains concrete tasks, file/API contracts, dependencies, acceptance tests, and a rollback note. Stages below are ordered; UI sketches and translation drafts may proceed in parallel after the contracts are set.

### Stage 1 — Hosting and security feasibility

Create the React/TypeScript/Vite and Worker workspace, Wrangler configuration, one named SQLite-backed Durable Object, isolated test/restore environments, local setup, lockfile, lint/typecheck/test commands, and a minimal `/api/v1/health` endpoint. Deploy the UI and API together on a Free `workers.dev` address. Prove SPA deep links, `/api` and nested API 404 behavior, missing-asset 404 behavior, SQL reads/writes, and native scrypt hashing/verification at the chosen work factor within the actual Free runtime; confirm the current documented storage ceiling. **Exit:** one repeatable deployment and measured security/usage proof; if the hashing proof fails, revise the hosting decision before Stage 2.

### Stage 2 — Users, invitations, and sessions

Implement schema migrations, one-time owner bootstrap, invitation issue/revoke/expiry, invite-only registration with phrase confirmation, seven-seat enforcement, password hashing, sign-in/out, session cookies, CSRF, authorization, and rate limits. **Exit:** owner plus six members can register; an eighth active user and reused invite fail, including simultaneous attempts; protected routes reject anonymous or unauthorized calls; secrets never appear in logs.

### Stage 3 — Recovery and manual rescue

Implement phrase reset with new-phrase confirmation and session invalidation, signed-in password change or phrase-only regeneration, operator-token redemption, and the Data Studio reset runbook. **Exit:** old phrases, used tokens, and sessions fail after successful rotation; old passwords fail when a new password was set, while phrase-only regeneration preserves the current password; an incomplete reset leaves the prior credentials intact; no mail or email-reset endpoint exists.

### Stage 4 — Board API

Seed columns and implement board read, owner column management, card create/edit/delete/assign/move, member deactivation effects, revision conflicts, and transaction-safe ordering. **Exit:** no card is lost or duplicated during concurrent moves; every card has one column and deterministic order; unauthorized column/member operations fail; assignments cannot target inactive users.

### Stage 5 — Board and account UI

Build invitation/registration/login/recovery screens, member management, the board, card editor, drag-and-drop, explicit move controls, loading/error/empty states, and responsive layout. **Exit:** seven-user-sized sample data works end-to-end with mouse, touch, and keyboard; stale moves reload visibly and stale edits retain unsaved form values; the recovery phrase is shown only at issuance and never persisted in browser storage.

### Stage 6 — Localization and accessibility

Complete all three dictionaries and language persistence, RTL/LTR styling, mixed-script behavior, localized form errors, screen-reader announcements, focus management, and keyboard-only checks. **Exit:** registration, reset, and board workflows pass in English, Hebrew, and Russian at desktop and mobile widths, with no missing translations.

### Stage 7 — Backup, hardening, and release

Implement export/isolated import, encrypted local backup script, restore drill, usage review, production security headers, dependency review, and deployment runbook. Run API/concurrency/security tests and end-to-end smoke tests on the actual Free deployment. **Exit:** the owner can restore an encrypted backup and carry out a lost-phrase database reset; all acceptance criteria above pass; current Free-tier terms and measured usage are recorded.

## 8. Final review criteria

During stage-plan review and implementation, verify that every requested feature maps to a stage: one shared board; column and card management; drag-and-drop with a non-drag fallback; user assignment; at most seven active users; invitation-based email/password login; phrase-only self-service recovery; manual database rescue; English/Hebrew/Russian; and correct RTL/LTR behavior. Confirm there is **one Cloudflare hosting account**, no paid dependency, and no email-reset path. Keep future additions out of the first-release subplans unless the product scope is changed explicitly.
