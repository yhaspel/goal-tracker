# Stage 7 — Backup, Hardening, and Release

**Status:** Ready to implement after Stages 1–6  
**Scope authority:** `personal-business-goals-dashboard-master-plan.md`  
**Deliverable:** A recoverable, secured, measured Free-tier production deployment and an operator runbook.

## Scope and prerequisites

Stages 1–6 must provide the deployed React/Worker/Durable Object application, schema migrations, accounts/recovery, board API, UI, and three-language accessibility work in an isolated Free **test** environment with disposable users. No real production household has been initialized. Use the existing Cloudflare Free account and `workers.dev` hostname; do not introduce a paid domain, email provider, or second hosting service. This stage implements independent encrypted local backups and a restore path in a separate Wrangler environment/namespace, validates release safety on the actual Free runtime, and only then initializes the production owner. The operator's local encrypted copies are not an app hosting platform.

Stage 1 must have an isolated restore environment bound to its own SQLite-backed Durable Object namespace. Production, test, and restore use distinct Worker/namespace bindings and operator secrets, but the same **server-fixed object name** (for example, `household`) so a validated namespace can be transferred later without changing the object ID lookup. The restore class export name must differ from every class name already provisioned on the live production Worker to avoid a transfer collision; if a prior rescue used that alias, choose and test a fresh class alias before the next transfer. A trusted `BACKUP_HOUSEHOLD_ID` in configuration identifies which household a backup may restore: production and its restore target must match, and a disposable test-source drill uses its own matching ID in the disposable target. The import route is deployed only in the restore environment; a production route or user-facing UI must not be able to select an arbitrary object name or import into production. Maintain a schema version and a known migration path. Check current Cloudflare documentation and account dashboard limits before release rather than relying only on the master plan's dated quotas. [Cloudflare Durable Object class exports](https://developers.cloudflare.com/durable-objects/reference/durable-objects-migrations/)

## Backup format, API, and operator tools

Create a versioned, deterministic export envelope with `formatVersion`, the application `schema_migrations` version, `createdAt`, table counts, a fixed household identifier, ordered records, and a SHA-256 digest. Define the digest input precisely as the canonical UTF-8 serialization of all envelope fields **except the digest field itself**; use a fixed table and record order and a tested canonical serializer. Do not use `PRAGMA user_version` for Durable Object SQLite. Include all durable application data needed to recreate the household: `app_state` bootstrap-consumed status, users and password hashes, `recovery_credentials` digests, invitation metadata/digests, columns, cards, and board revision/state. Exclude live sessions, rate-limit entries, pending registrations, `pending_credential_rotations`, and all one-time operator tokens/challenges; document that users must sign in again and unfinished signups/recoveries restart after restore. Never export plaintext credentials, invite codes, recovery phrases, session tokens, or secrets. Read all included tables from **one coherent SQLite snapshot** and validate referential integrity and the seven-active-user limit on export and import. For the Stage 4 maximum of 500 cards and 20 columns, bound the export to 16 MiB and measure a full-size, maximum-length multilingual sample on Free. If a coherent one-response snapshot cannot complete within the measured Free runtime, block release and revise this plan with a concrete version-pinned chunked-snapshot design; never mix records from different board revisions. The export must not alter application state.

Implement `GET /api/v1/operator/export` in production and restore, and `POST /api/v1/operator/import` **only** in the restore environment. Both are handled by the bound Durable Object and require a separate 32-byte random `BACKUP_OPERATOR_SECRET` stored as a Cloudflare secret and supplied by the trusted local CLI in an `Authorization: Bearer` header, compared in constant time. Require HTTPS, rate limits, `Cache-Control: no-store`, and JSON content types that cannot be interpreted as the SPA. The operator credential is never placed in browser code, query strings, logs, or backup files. Do not authorize export solely with the household owner's ordinary session, since owner lockout is one reason for restoring. Give operator import a separate 16 MiB request-body limit; member and auth endpoints keep their smaller limits. The front Worker checks size and forwards the stream without parsing or hashing the full backup, keeping its Free CPU work short; the Durable Object does authorization, parsing, validation, and SQL. Import accepts the versioned envelope only into a **pristine restore object**: migrations and the three default seed columns may exist, but no users, cards, invitations, or prior import marker may exist and the board must still be at its seed revision. Add a restore-only `restore_import_marker` table. Verify the format/digest, configured household identifier, schema compatibility, IDs, references, order uniqueness, and counts **before** the import transaction. Inside the one synchronous transaction, recheck that the target still has no marker, users, cards, or invitations and has only the seed columns/revision; then remove the seed columns, insert exported application records, and write the marker. Reject a non-pristine target and malformed or future-version backups before writing any imported records. A failed transaction leaves the seed state unchanged. The target schema and indexes already exist from migrations; transform compatible older envelopes into that schema before insertion, or reject unsupported versions. Imported sessions remain absent. Verify board counts, revision, assignment references, and login/recovery using the escrowed secrets. A new-account restore cannot verify old recovery phrases without the original recovery-digest secret.

Provide a local backup CLI (`scripts/backup.ts`) that obtains the operator secret from a protected local source, downloads the export over HTTPS, validates the envelope, and encrypts it locally using Node `crypto` AES-256-GCM with a random 96-bit nonce and a random 256-bit key stored outside the backup directory. Version the encryption envelope and include the nonce and authentication tag. Stream into a restricted temporary encrypted file, atomically rename it, then verify decryption/digest before declaring success; never leave an unencrypted temporary file. File names may contain date and schema version but no user data. Retain four weekly and three monthly encrypted copies, pruning only after a new verified copy exists. Schedule weekly execution on the operator's machine or document a manual weekly routine; if the machine is off, the runbook must require a catch-up backup. Escrow the encryption key, `RECOVERY_DIGEST_KEY`, `CSRF_SECRET`, `RATE_LIMIT_KEY`, and operator secret separately from the encrypted backup files, with restore instructions and access restrictions. Do not print secrets to terminal output or command-line arguments.

Cloudflare's SQLite-backed Durable Object point-in-time recovery is an additional short-term recovery tool, not the only backup. Document how to inspect available recovery points and recover from a bad deployment without overwriting newer production writes by accident. Every monthly restore drill provisions a **fresh isolated restore Worker/namespace** with its own server-fixed `household` object, configures the matching `BACKUP_HOUSEHOLD_ID` and source `RECOVERY_DIGEST_KEY` from escrow in that isolated target, imports a recent encrypted copy, validates it, and then removes the drill Worker/namespace only after recording success; never reuse an object with a `restore_import_marker`. Namespace deletion destroys test data permanently, so the CLI/runbook must verify the target is the expendable restore namespace and never issue a delete against production. A production replacement, if ever needed, is a separate maintenance action: pause writes and take a fresh pre-action backup; import/validate a new isolated restore namespace; use Cloudflare's documented `exports` **four-deploy transfer** (`expecting-transfer` on production target without a binding, `transferred` tombstone on restore source, then production binding after transfer commits) for a restored class alias not previously provisioned on production; switch production's binding to it while keeping the server-fixed object name; remove/disable the source import Worker; smoke-test, then reopen writes. Keep the old production class/namespace unbound and intact until success. Test this entire transfer on disposable Workers before recording it as operable; never add an import route to the live production Worker. [Cloudflare class transfer procedure](https://developers.cloudflare.com/durable-objects/reference/durable-objects-migrations/)

## Acceptance tests and adversarial cases

- An encrypted weekly backup can be decrypted with its separately held key and imported into a pristine isolated restore object containing only migrations and default seed state. Counts, IDs, board revision, card order, assignments, and password/recovery verification match the source. Live sessions do not survive. A second import is rejected by the restore marker.
- A corrupt, truncated, tampered, future-version, wrong-household, or reference-invalid export is rejected before data changes. A **production** export is accepted by the matching isolated restore household, which is the point of the drill. A failed import leaves the pristine restore seed state unchanged. A lost encryption key or recovery-digest secret is reported as a blocking operational failure, not silently ignored.
- Production has no callable import route, and an ordinary owner/member/anonymous request cannot access export. Secrets do not appear in static assets, network URLs, logs, process arguments, or backup filenames. A cache cannot serve one user's private API response to another.
- The owner can complete a lost-phrase reset by following the Data Studio runbook with offline verification. A wrong, expired, or redeemed operator token fails; successful redemption invalidates old sessions, password, and phrase and creates a newly confirmed phrase. No mail service or email-reset endpoint exists.
- An eighth active user, duplicate/expired/reused invite, inactive assignee, unauthorized owner action, stale revision, and concurrent card moves are rejected or resolved exactly as earlier stages specify. Board order remains deterministic after reload.
- Browser smoke tests pass in English, Hebrew, and Russian in test, including Hebrew RTL, mixed-script card content, touch and keyboard movement, phrase reset, and small screens. No essential action requires a pointer. Production is initialized with the real owner only after export, backup encryption, isolated restore, and runbook steps pass.
- The runbook includes weekly backup, four-weekly/three-monthly retention, monthly restore drill, point-in-time recovery, Free quota review, manual rescue SQL, and production replacement steps. One dry-run operator can follow it without undocumented credentials or assumptions.
- Current Free-tier terms and measured use are recorded; the deployment remains on one Cloudflare Free account with no recurring charge and no hidden paid dependency. The app communicates best-effort availability rather than promising an SLA.

## Delivery and exit gate

Deliver export/restore code and tests, the encrypted local backup CLI, a reviewed operator runbook, documented secret escrow, security configuration, release checklist, measurements, and a successful isolated restore report. Stage 7 is complete only after the actual Free deployment passes the entire master plan's exit criteria, including manual lost-phrase rescue and a restore from an encrypted copy. If any feasibility or security gate fails, release is blocked until the plan or implementation is corrected.

## Rollback

Before a deployment or schema change, take and verify a fresh encrypted backup. If a new Worker version fails while the data schema is compatible, redeploy the previous version; do not roll back code across an incompatible migration. If data is damaged, stop writes, preserve the current object for investigation, and follow the documented point-in-time or validated backup recovery procedure. Never import into production as an automatic rollback. If backup verification fails, keep the prior verified copies and block release or destructive maintenance until a new valid copy exists.
