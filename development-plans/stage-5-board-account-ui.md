# Stage 5 — Board and Account UI

**Status:** Ready to implement after Stages 1–4  
**Scope authority:** `personal-business-goals-dashboard-master-plan.md`  
**Deliverable:** One responsive React application for the single shared board and every non-operator account flow.

## Scope and dependencies

Build a small, usable interface for invitation registration, sign-in/out, phrase recovery, account settings, owner member/column management, and card work. Support one group, one board, and seven active users at most. Cards contain only title, optional description, optional active assignee, column, and position. The default columns are To Do, In Progress, and Done. The first implementation may use English copy, but every UI string must pass through the typed translation interface completed in Stage 6. Do not add goals, separate boards, labels, due dates, attachments, notifications, or AI prompt integration.

Stages 2–4 must deliver the versioned `/api/v1/` contracts and error codes for authentication, registration, recovery, member management, board reads, columns, cards, and revision conflicts. The UI must use those published contracts as the single source of truth; do not define a second API shape in components. Stage 1 must already route the SPA and API separately. Expand its navigation allowlist for the actual Stage 5 paths (`/bootstrap`, `/account`, `/members`, plus any nested account/recovery pages); direct navigation to each must work without allowing arbitrary unknown paths to return the shell. Work on UI shells may start earlier with contract fixtures, but integration cannot be accepted until the real API is available.

## Implementation structure and contracts

Use the Stage 1 workspace layout:

| Area | Responsibility |
| --- | --- |
| `web/src/api/client.ts` and `shared/` | Typed same-origin `fetch` client and canonical API types, credentials, CSRF header, error mapping, abort handling; no token storage. |
| `web/src/auth/` | Session guard, owner bootstrap, sign-in, invite registration, phrase confirmation, self-service reset, operator-token redemption, account settings. |
| `web/src/board/` | Board loader, column/card views, card editor, owner column controls, movement adapter, revision handling. |
| `web/src/members/` | Owner invitations, revoke/deactivate controls, active member selector. |
| `web/src/i18n/` | Typed translation keys and locale hook; dictionaries and direction behavior are completed in Stage 6. |
| `web/src/styles/` | Responsive layout, logical CSS properties, focus styles. |
| `tests/` | Contract fixtures and workflow tests that exercise user-visible behavior. |

The API client must send cookies with same-origin requests. Read `{data:{user,csrfToken}}` from `GET /api/v1/auth/session`; hold its session-bound CSRF token in memory and send `X-CSRF-Token` on established-session mutations. A reload re-fetches it. Let the browser supply the `Origin` header on mutations; JavaScript must not attempt to set this forbidden header. Pre-auth mutations have no session CSRF header, but the server still checks Origin. Read success through `{data:...}` and errors through `{error:{code,message,details?}}`; render safe, localized messages from error codes without echoing secrets or server internals. Treat `401` as an expired session, `403` as a permission failure, `404` as missing/inaccessible data, and `429` as rate limiting. Branch on the `409` **code**: `revision_conflict` triggers reload/draft preservation; `board_full`, `column_limit`, `last_column`, and `column_not_empty` show the relevant limit/refusal without pretending a concurrent edit occurred. Never retain a password, invitation code, recovery phrase, pending/challenge token, or operator token in URL history, analytics, logs, persistent browser storage, or a global app store. Use manual code-entry fields; no recovery code is accepted through a URL. Keep phrase, pending/challenge token, and password values only in mounted form memory and clear them on success, cancel, route change, and sign-out. Never print them to the console. All auth/recovery responses and screens use `Cache-Control: no-store`.

`GET /api/v1/board` supplies `{data:{boardRevision,columns,activeMembers}}`. All column/card mutations use the last confirmed `boardRevision` in their JSON body; stale writes receive `409` with `error.code='revision_conflict'` and the current revision in `error.details.boardRevision`. A successful mutation adopts the returned revision and server state. On `409`, discard speculative board ordering, fetch the current board, announce that the attempted change was not saved, and retain unsaved card-form values for the user to review and resubmit. Background refetches update the board display but **never replace an open card editor draft** or its touched fields; when the underlying card changed, show a conflict notice and offer to compare/reapply the draft. A mutation failure must never leave a card displayed at a position that the server did not save. Disable duplicate submissions while a request is in flight; do not infer success from animation.

## Ordered work

1. **Typed client and navigation.** Implement a same-origin API adapter and route guards for guest, active member, and owner views. Use an initial session read to avoid flashing protected data. Bootstrap, registration, login, and phrase/operator recovery are guest-only because Stages 2–3 reject a live session with `403 already_authenticated`; a signed-in person uses the account credentials flow or signs out first. Add loading, empty, offline/network, expired-session, and permission states. Keep the UI resilient to a failed request without showing the API's raw response body.
2. **Account screens.** Implement one-time owner bootstrap, invitation entry, bound-email registration, password creation, one-time phrase display and confirmation, sign-in, sign-out, phrase-based password reset, manual operator-token redemption, signed-in password change, and phrase regeneration using the Stage 2–3 state machines. Query `GET /api/v1/auth/bootstrap/status` before showing bootstrap entry; once consumed, the UI closes the path, while the API remains authoritative. Owner/invite preparation calls `POST /api/v1/auth/bootstrap/prepare` or `/auth/registration/prepare`, passing the guest's chosen `language`, then confirmation calls `POST /api/v1/auth/registration/confirm` with the in-memory `pendingToken` and re-entered `recoveryPhrase`. Login/logout use `/api/v1/auth/login` and `/auth/logout`. Stage 3 uses the paired `/api/v1/recovery/phrase/start` and `/confirm`, `/api/v1/recovery/operator/start` and `/confirm`, and `/api/v1/account/credentials/start` and `/confirm` routes. Operator start requires manually entered email and reset token. Signed-in credentials start accepts current password and optional new password; omitting the new password regenerates the phrase only. Make phrase confirmation explicit before activation or rotation. Provide a copy control and a clear save instruction, but do not download or auto-save the phrase. If a pending flow expires or reloads before confirmation, show the matching restart path: bootstrap if still available, invitation registration if the invite remains valid, or the relevant recovery method; never pretend activation succeeded. Explain in the UI that there is no email reset and a lost phrase requires contacting the owner offline.
3. **Owner account administration.** Use `GET/POST /api/v1/invitations`, `DELETE /api/v1/invitations/:id`, `GET /api/v1/members`, and `PATCH /api/v1/members/:id` with `{status:'inactive'}`. Build invite creation for a specified email, display a newly issued code once, show pending invite status/expiry, revoke invitations, list members, and deactivate a member with confirmation. Show the maximum of seven active seats and a useful error if a concurrent acceptance fills the final seat. Never show or retrieve an old invite code. The owner cannot deactivate themself. Deactivated members disappear from assignment choices after a refresh.
4. **Board read and editing.** Render one shared board with columns in server order and cards in deterministic card order. Use `POST /api/v1/cards` and `PATCH/DELETE /api/v1/cards/:id` for create/edit/delete. Build card create/edit dialogs for title, description, and one optional active assignee. Enforce client-side lengths as guidance, while rendering the API's authoritative validation errors. Explain the Stage 4 limits of 500 cards and 20 columns when a limit is reached; never show a truncated board as complete. Provide delete confirmation and an undo-free success/failure response. All user-authored text is rendered as text, not HTML; apply `dir="auto"` to card content. Refetch on successful mutations, tab focus, and a modest interval only while the board is visible; cancel polling when hidden/unmounted. Avoid overlapping fetches and stale-response overwrite by aborting or sequencing requests. Keep editor drafts separate from refetched card objects.
5. **Owner column controls.** Use `POST /api/v1/columns`, `PATCH/DELETE /api/v1/columns/:id`, and `POST /api/v1/columns/:id/move` for reordering. Add, rename, reorder, and remove empty columns, with a confirmation for removal. Prevent removal of the last column. Show the server's conflict or nonempty-column refusal, preserving the current board. The three seed labels use translation keys until renamed; custom names stay verbatim.
6. **Card movement.** Integrate the pinned `@dnd-kit/react` API for pointer and touch drag across columns and within a column, plus its keyboard sensor. Convert the library's destination into `POST /api/v1/cards/:id/move` with card ID, destination column, insertion point, and `boardRevision`; do not calculate final persisted positions only on the client. Also provide explicit **Move to column**, **Move up**, and **Move down** actions on every card, with disabled edge actions. Make movements reachable without dragging on narrow screens. A single move is one API request; handle network failures and `409` by restoring server order and announcing the outcome.
7. **Responsive and interaction polish.** Keep actions usable at 320 CSS pixels and common mobile widths, with horizontal board scrolling when necessary. Give dialogs a proper label, keyboard dismissal where safe, focus trap, and focus return to the triggering control. Preserve input values on recoverable failures. Provide clear pending states without hiding other users' committed changes. Avoid background scroll traps and pointer-only affordances.
8. **Integration and deployment check.** Run the actual Worker UI against the Stage 2–4 API in the isolated Free **test** environment with disposable users. Exercise owner and member sessions in separate browsers, including a real conflict. Verify a `workers.dev` deep link loads the right screen and that an unknown API path remains a JSON 404. Do not initialize a real production household in this stage.

## Acceptance tests

- One owner and six members can complete invitation, phrase confirmation, sign-in, and board use. An eighth invitation acceptance is rejected by the API and reported intelligibly; the UI cannot bypass the seat limit.
- Registration and both reset paths show a newly generated recovery phrase only from the prepare/start response; confirmation asks for re-entry and never returns it. A refresh or completed flow cannot reveal it again. Browser storage, navigation history, console output, and error logs contain no credentials or recovery material.
- Anonymous users cannot see board data. Members cannot use owner controls even by invoking an API call directly; the UI handles `401` and `403` without exposing protected data. A live session is directed away from guest-only bootstrap, registration, login, and phrase/operator reset; a server `already_authenticated` response offers sign-out or the signed-in account route.
- A member can create, edit, assign, unassign, move, and delete a card. Assigning an inactive user is refused and refreshes the available choices. An empty title, overlong title/description, invalid column, and duplicate submission show safe errors without losing unrelated work.
- The owner can add, rename, and reorder columns. Removing a nonempty or last remaining column fails safely. A member cannot change columns.
- Pointer, touch, keyboard drag, and the explicit move controls all persist correct order after a fresh reload. A dropped card does not disappear, duplicate, or persist in two columns.
- With two sessions editing the same revision, the loser receives a visible conflict; moves revert to server order, while unsaved editor fields remain available for review and retry. A background focus/poll refetch during an open editor never overwrites typed values. A failed network request behaves similarly.
- Mobile-width navigation, card edit, assignment, column scrolling, and account flows require no hover or horizontal page overflow beyond the board's intended scroll container.
- Stage 5 UI workflow tests and typecheck pass. A deployed smoke test covers login, card creation/move, phrase reset, and owner invitation/deactivation.

## Delivery and exit gate

Deliver working React routes/components, the typed API adapter, styles, meaningful workflow tests, and a short UI interaction note in the repository. Record the pinned drag library version and any API contract change agreed with Stages 2–4. Stage 5 is complete when all account and board workflows run on the Free **test** deployment with seven-user-sized disposable sample data and mouse, touch, and keyboard input; conflicts are visible and recoverable; recovery material is not persisted in browser storage. Stage 6 then completes translation and accessibility validation, so Stage 5 must not hard-code visible copy.

## Rollback

Revert to the previous known-good static UI bundle/Worker deployment while preserving the Durable Object and its data. Do not roll back to a UI that sends an incompatible API payload; if contracts changed, deploy a compatible adapter first. On a movement defect, disable drag interaction and retain the explicit move controls until fixed; never silently discard or rewrite persisted cards.
