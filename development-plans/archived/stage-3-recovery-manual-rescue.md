# Stage 3 — Recovery and Manual Rescue

**Status:** Implementation-ready subplan  
**Parent:** [Family Kanban Board master plan](personal-business-goals-dashboard-master-plan.md), Stage 3  
**Prerequisite:** Stage 2 exit gate passed. Its session, CSRF, rate-limit, scrypt, phrase-digest, and migration primitives are available. Stages 1–6 use disposable accounts in an isolated Free test environment; production initialization waits for Stage 7 backup tooling.  
**Outcome:** A member can rotate credentials with a saved recovery phrase, a signed-in member can change a password and regenerate the phrase, and an operator can rescue a member who lost the phrase through a short-lived database-issued token. No email reset exists.

## Scope and fixed contracts

Use the Stage 2 JSON convention: successful responses are `{ "data": ... }`; failures are `{ "error": { "code": "stable_code", "message": "safe message" } }`. Use `POST` under `/api/v1/`. All writes require an exact same-origin `Origin`; signed-in writes also require the `X-CSRF-Token` returned by `GET /api/v1/auth/session`. Phrase and operator-token routes are pre-auth: reject a caller carrying a live session with Stage 2's `403 already_authenticated` error and direct them to sign out or use the signed-in credential flow. Anonymous requests have no session-bound CSRF value and instead rely on their high-entropy credentials, short challenge lifetime, and persistent per-IP/per-account rate limits. Set `Cache-Control: no-store` on every credential response, including errors, and never log request bodies, phrases, tokens, or passwords.

| Flow | Start endpoint and request | Confirm endpoint and request | Successful confirmation |
| --- | --- | --- | --- |
| Saved phrase | `/api/v1/recovery/phrase/start` with `{email, recoveryPhrase, newPassword}` | `/api/v1/recovery/phrase/confirm` with `{challengeToken, newRecoveryPhrase}` | Rotates password and phrase; revokes every session; requires a fresh login |
| Lost phrase | `/api/v1/recovery/operator/start` with `{email, resetToken, newPassword}` | `/api/v1/recovery/operator/confirm` with `{challengeToken, newRecoveryPhrase}` | Consumes operator token, rotates password and phrase, revokes every session; requires a fresh login |
| Signed in | `/api/v1/account/credentials/start` with `{currentPassword, newPassword?}` | `/api/v1/account/credentials/confirm` with `{challengeToken, newRecoveryPhrase}` | Rotates the phrase and, if supplied, the password; revokes every session including the current one; requires a fresh login |

Each successful `start` returns `{data:{challengeToken,recoveryPhrase,expiresAt}}` with the **new** 12-word phrase only once. The browser keeps both values in component memory until confirmation; neither goes into local/session storage, a URL, analytics, or a service-worker cache. The person must re-enter the new phrase; the UI in Stage 5 explains that closing or refreshing before confirmation leaves the old credentials in force. Each successful `confirm` returns `{data:{rotated:true}}`, clears the session cookie where present, and does not issue a new session. Omitting `newPassword` in the signed-in flow regenerates only the phrase and deliberately leaves the current password valid; the person still reauthenticates because all sessions are revoked. All invalid email/phrase/token combinations use generic failure text; only an authenticated account flow may give account-specific errors. Do not add a password-reset route that sends or accepts an email link.

Stage 2 owns `users` (including `credential_epoch`, password hash and scrypt parameter version), `recovery_credentials.phrase_digest`, sessions, rate limits, and the keyed phrase-digest helper. Normalize phrases only for case and whitespace, exactly as Stage 2 does. The same pinned 2,048-word list and cryptographic random generator create each replacement phrase. The Stage 2 `RECOVERY_DIGEST_KEY` Cloudflare secret also signs operator-token digests with a **different domain prefix** from phrase digests. Never store raw phrase, reset token, challenge token, or new password.

The Stage 2 allowed-email policy also applies here. Require the target user to be active **and currently allowlisted** when any recovery or credential-rotation flow starts and again when it confirms; use generic pre-auth errors so callers cannot test list membership. When the owner removes an email, revoke that user's pending rotations and unused operator-reset tokens as well as sessions. Adding an email back does not revive old challenges or tokens; a new recovery attempt is required. Recheck this policy inside each confirmation transaction so a concurrent removal wins safely.

Stage 7's independent backup must preserve `users` and `recovery_credentials` but exclude `pending_credential_rotations`, live `operator_reset_tokens`, sessions, and rate-limit state. Interrupted resets can restart after restore; an operator can issue a new token. Escrow `RECOVERY_DIGEST_KEY` separately from the backup so restored phrase verification remains possible.

## Database and code changes

Add an additive Stage 3 migration in `worker/src/db/migrations.ts`:

- `pending_credential_rotations`: opaque UUID `id`, `user_id`, `method` (`phrase`, `operator`, or `signed_in`), `challenge_digest` (unique), nullable `new_password_hash` (the complete Stage 2 versioned encoded hash record; null only for phrase-only regeneration), `new_phrase_digest`, `expected_credential_epoch`, nullable `expected_source_digest` (old phrase digest for `phrase`, full password hash record for `signed_in`, null for `operator`), nullable `source_session_id` (required for `signed_in`), nullable `operator_token_id` (required for `operator`), `created_at`, `expires_at`. Store UTC ISO timestamps in the same fixed format as Stage 2. Index `user_id` and `expires_at`. Expire rows after **10 minutes**; prune expired rows on relevant requests and maintenance.
- `operator_reset_tokens`: opaque UUID `id`, `user_id`, unique `token_digest`, `expected_credential_epoch`, `created_at`, `expires_at`, nullable `consumed_at`, `issued_by`, and a short audit `reason` that contains no secret. Index `user_id` and `expires_at`. Operator tokens expire after **15 minutes** and can be consumed once.
- If Stage 2 already created either table, make this migration an idempotent constraint/index upgrade rather than a second table. Keep the schema version monotonic; do not implement a destructive down migration.

Implement credential rotation orchestration in `worker/src/auth/recovery.ts`, route handlers in `worker/src/routes/recovery.ts`, typed requests/responses in `shared/api.ts` (or the Stage 1 shared API module), a trusted local `scripts/create-operator-reset-token.ts`, and `docs/operator-lost-phrase-reset.md`. Reuse Stage 2 authentication, origin/CSRF, scrypt, HMAC, phrase generation, validation, error, and rate-limit modules. Add integration tests under `tests/` against an isolated local Durable Object; run a smaller smoke test on the actual Free deployment.

## Ordered implementation tasks

1. **Migration and secrets.** Define schema constraints and indexes, an explicit 10-minute pending challenge lifetime, and 15-minute operator-token lifetime. Extend Stage 2's owner allowed-list replacement transaction to revoke removed users' pending rotations and unused operator tokens once these tables exist. Reuse Stage 2's exact phrase HMAC prefix `recovery-v1|`; use a distinct `operator-token:v1|` prefix for operator-token HMACs. Verify `RECOVERY_DIGEST_KEY` exists only as a Cloudflare secret and in the separate operator secret escrow, never in SQL or source control. Add expiration cleanup with bounded deletes.
2. **Prepare without changing credentials.** For each `start`, validate request shape and password policy, apply persistent per-IP and per-account limits, and read the relevant user/credential/token and `credential_epoch`. Match an operator token to the supplied normalized email as well as its digest. Verify the old phrase, operator token, or current password. When a new password is supplied, reject reuse of the current password (checking its existing scrypt hash outside a transaction) and compute the **new password scrypt hash outside any SQLite transaction**; phrase-only regeneration reuses the existing password record. Generate a new phrase whose digest differs from the current one and a random challenge token with at least 128 bits of entropy, then digest both. Insert a pending row in a short `ctx.storage.transactionSync()` callback only if the account is active, currently allowed, and the credential epoch and source credential/token still match the snapshot. Return the new phrase only after insertion succeeds. Failed validation must not reveal whether an email exists or is allowed; use a dummy verification path where needed to reduce enumeration.
3. **Confirm atomically.** Validate challenge and re-entered phrase, then in one synchronous `ctx.storage.transactionSync()` callback re-read the pending row and active user, require current allowed-list membership, and check its expiry, expected epoch, challenge digest, new phrase digest, and original source digest or unconsumed operator token. For a signed-in flow, also require its source session to remain live. Update `users.password_hash` with the new complete encoded record only when supplied, update `recovery_credentials.phrase_digest` and its version, increment `credential_epoch`, mark the operator token consumed where applicable, delete all sessions for the user and all their pending rotations, and commit. Clear the browser cookie if present. Do not `await` inside the transaction callback. If any check fails, throw and roll back the whole transaction. A second confirmation or competing pending flow must fail without partial changes.
4. **Operator issuance and Data Studio runbook.** The operator verifies the person's identity through an established offline channel; an email address alone is insufficient because the app does not verify email ownership. In Cloudflare Durable Object Data Studio, look up the active, currently allowlisted user's ID and `credential_epoch` by the Stage 2 `users.email_norm` column joined to `allowed_emails`. Pass those values to the trusted local script; it generates a cryptographically random 32-byte base64url token, calculates its domain-separated HMAC hex digest, and prints the raw token once plus fully quoted SQL containing only the digest, ID, epoch, timestamps, operator identifier, and nonsensitive audit reason. Insert that SQL into `operator_reset_tokens` through Data Studio, check that exactly one row was inserted, and share the raw token through the established offline channel. The runbook must include the exact lookup/insert/revoke SQL matching the final schema, safe quoting instructions, a 15-minute expiry, evidence to record without secrets, and how to repeat the operation if it expires. Only the Cloudflare account operator can use Data Studio; an in-app owner role alone cannot directly edit SQL.
5. **Abuse and operational handling.** Rate-limit all starts and confirmations; allow at most three unexpired pending rows per user and prune expired rows with bounded deletes. Never expose the list of valid reset tokens or account existence. Record security events by user ID or anonymized identifier, method, timestamp, and result only. Preserve the Stage 2 `Secure; HttpOnly; SameSite=Lax; Path=/` cookie behavior. Document that losing both the phrase and operator access requires restoring operator access, not an email fallback.

## Acceptance and adversarial tests

- A valid saved phrase starts a rotation, displays a new phrase exactly once, and a matching re-entry commits it. Reusing the current password as `newPassword` is rejected. The old password, old phrase, all pre-existing sessions, and reused challenge fail after a successful password rotation; the new password works after a fresh login. A wrong new-phrase entry, expired challenge, closed tab, failed hash, or interrupted transaction leaves the old password, phrase, and sessions valid.
- A signed-in password change requires the current password, live session, exact `Origin`, and CSRF header. It rotates the phrase and invalidates the current and other-device sessions only on confirmation; the old password then fails. A signed-in phrase-only regeneration also requires the current password and rotates the phrase and sessions, but leaves the password valid. A concurrent logout/deactivation or credential rotation makes the pending confirmation fail safely.
- A correctly inserted operator token works once and expires in 15 minutes. Wrong, reused, revoked, expired, or wrong-user tokens cannot start or complete a reset. Two concurrent confirmations of one token result in exactly one success. An incomplete operator reset does not consume the token or change credentials before expiry.
- Removing a member's email during any pending recovery flow revokes its challenge and unused operator token. No recovery start or confirmation succeeds while the email is absent from the allowed list; re-adding it requires fresh credentials/challenges, without exposing list membership to an anonymous caller.
- Concurrent phrase and operator starts may each create a pending challenge while the credential epoch is unchanged. If both challenges are confirmed, only the first confirmation commits and advances `credential_epoch`; the other receives a generic conflict and cannot overwrite the first result. Pending rows contain hashes/digests only, and no secret appears in logs, SQL exports, browser storage, URLs, or error bodies.
- Anonymous POSTs with missing/foreign `Origin`, signed-in POSTs with absent/bad CSRF, pre-auth recovery calls with a live session, oversized bodies, malformed phrases, short/common passwords, and rate-limit excess are rejected with the Stage 2 error format and suitable `400`/`401`/`403`/`429` responses. A route audit confirms there is no email-reset endpoint, mail library, or mail service credential.
- Run the complete Data Studio procedure in an isolated environment with an active test account, including token creation, insertion, successful redemption, revocation, expiry, and audit entry. The real Free deployment passes a scrypt and confirmation timing check without holding a SQLite transaction open during hashing.

## Exit gate and rollback

Stage 3 is done when all three flows work end-to-end in the isolated Free test environment, the operator can follow the documented SQL rescue without reading or changing plaintext credentials, all negative and concurrency tests pass, and the Stage 5 UI contract above is stable. If a test deployment fails, disable the faulty route or rebuild the disposable test object from fixtures and roll forward with a fix. An app-code rollback may leave additive tables and expiring pending rows in place, but must not restore old credential data or re-enable consumed tokens. Verify login still works before reopening recovery. Do not initialize production accounts before Stage 7's export, encrypted backup, and restore drill are complete.
