# Stage 2 — Users, Invitations, and Sessions

**Parent:** [Family Kanban Board master plan](../personal-business-goals-dashboard-master-plan.md)  
**Status:** Complete on 2026-09-13. See the [Stage 2 completion report](../../docs/stage-2-completion.md).  
**Dependency:** Stage 1 exit gate has passed in the deployed Cloudflare Free runtime.  
**Outcome:** One disposable test owner (the group's only admin) can maintain an allowed-email list. After owner bootstrap, only allowlisted invitees can register and only allowlisted active accounts can access the group. The owner and up to six members can complete phrase-backed registration, sign in, use protected endpoints, and sign out. No recovery/reset operation is implemented until Stage 3; no real production account is created before Stage 7.

## Scope and boundaries

Implement the authentication foundation and account API in the single named SQLite-backed Durable Object. The front Worker continues to route and bound requests, but **all** identity, seat, role, session, allowed-email, and CSRF checks occur inside the Durable Object. The existing `owner` role is the group's **only admin**; no second admin role or admin account is added. Stage 2 delivers the owner-only allowed-email API; Stage 5 adds its settings UI as a multiline textbox with one email per row. This stage proves API behavior with integration tests and a small manual API script. There is no email delivery or email verification. An email address is a unique login identifier and invite target, not proof that the registrant controls that mailbox.

Stage 2 also implements owner-only member deactivation and session revocation. Once board state exists, Stage 4 extends activation, deactivation, and allowed-list updates to increment the board revision when the eligible active-member list changes; deactivation and allowlist removal also clear affected current card assignments in the same transaction. Deactivation is irreversible in the first release; a freed seat may be used by a different email, while the old user row remains for historical references. The owner cannot deactivate themself. Stage 3 owns phrase reset, signed-in password change, phrase regeneration, operator-token redemption, and the manual reset runbook.

The allowed-email list is an additional gate, not a replacement for single-use invitations. Bootstrap inserts the owner email into the list atomically; the owner can never remove it. The list holds at most seven distinct normalized emails including the owner. An email absent from the list cannot receive an invitation, prepare or confirm registration, log in, or use an existing session. Removing an email immediately revokes that account's sessions, unused invitations, and pending registrations. It does **not** deactivate an existing user or free their active seat; adding the email back permits that still-active user to sign in again, while an inactive user remains inactive. The owner uses the separate irreversible deactivation action to free a seat. Show this distinction in the Stage 5 settings UI before saving changes.

There is still only one group and one board, selected by the server-fixed Durable Object name. The client cannot choose a group through a request field or URL. Stage 4 grants every active, allowlisted member the same card edit/move/assignment permissions across the shared board; card creator and assignee IDs do not restrict editing. The owner alone manages the allowed list, invitations, members, and columns.

## Prerequisites and secrets

Keep the Stage 1 scrypt parameters and benchmarked implementation unchanged: native `node:crypto` scrypt `N=2^14,r=8,p=5`, a unique random salt of at least 16 bytes, a 32-byte derived key, and a versioned encoded record. Hashing is done before any synchronous SQL transaction; transaction callbacks cannot contain async work. Recheck the Stage 1 benchmark if runtime or dependency versions change. [Cloudflare's SQLite transaction API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/) requires a synchronous callback.

Configure distinct Cloudflare secrets for `BOOTSTRAP_SECRET` (at least 256 random bits, removed after owner activation), `RECOVERY_DIGEST_KEY` (keyed phrase digest), `CSRF_SECRET` (reissuable session-bound CSRF token), and `RATE_LIMIT_KEY` (pseudonymous rate-limit keys). Use disposable values in the isolated test environment; Stage 7 provisions and escrows independent production values before real owner activation. Do not print them or commit local secret files. Before opening bootstrap on any hostname, verify the secret is present and the route rejects a missing secret. The fixed production DO name remains server-owned.

## Data and migration contract

Add schema migration version 2 to `worker/src/db/migrations.ts` using the explicit `schema_migrations` table from Stage 1; do not use `PRAGMA user_version`. Use opaque UUID primary keys, UTC ISO-8601 timestamps, parameterized SQL, unique indexes, and validated references. The schema must support the following fields and constraints (column spellings may differ only if the typed repository interface maps them exactly):

| Table | Required state and constraints |
| --- | --- |
| `app_state` | Singleton row `bootstrap_consumed`, `allowlist_revision INTEGER NOT NULL DEFAULT 0`, and creation timestamp. Owner activation changes the flag once, inserts the owner email into the allowed list, and sets the revision to 1 in one transaction. |
| `users` | `id`, `email_norm UNIQUE`, `password_hash`, `role` (`owner` or `member`), `status` (`active` or `inactive`), `language` (`en`, `he`, `ru`; default `en`), `credential_epoch INTEGER NOT NULL DEFAULT 1`, created/updated timestamps. A unique partial index on `role='owner'` plus the bootstrap transaction prevents a second owner. Stage 6 adds the signed-in language preference endpoint. |
| `allowed_emails` | `email_norm PRIMARY KEY`, `created_at`. At most seven rows including the owner; only the owner can replace this set through the API. No invitation or account row is created merely by adding an email. |
| `invitations` | `id`, `email_norm`, `code_digest UNIQUE` (SHA-256 of the 128-bit random code), `created_by`, `created_at`, `expires_at`, nullable `consumed_at` and `revoked_at`. A code is usable only if unexpired, unrevoked, and unconsumed. |
| `pending_registrations` | `id`, `kind` (`bootstrap` or `invite`), `email_norm`, nullable `invitation_id`, `password_hash`, `phrase_digest`, `pending_token_digest UNIQUE`, `expires_at`, `failed_confirmations`, `created_at`. No plaintext password, code, token, or phrase. |
| `recovery_credentials` | `user_id UNIQUE`, `phrase_digest`, `version`, `created_at`. Stage 3 rotates these values. |
| `sessions` | `id`, `user_id`, `token_digest UNIQUE`, `created_at`, `expires_at`, nullable `revoked_at`. Index live lookup by token digest and user ID. |
| `rate_limits` | HMAC-derived `bucket_key`, window start, count, and expiry. Expired rows can be purged opportunistically. |

Stage 3 creates `operator_reset_tokens` with its final operator audit/epoch fields; Stage 2 does not create a partial version of that table. Stage 4 later adds `board_state`, `columns`, and `cards`.

Normalize an email by trimming and lowercasing a conventional ASCII email address, then validate length (3–254 bytes), one `@`, no spaces/control characters, and a plausible domain. The same function is used for the allowed list, invitations, registration, and login; tests cover case, surrounding spaces, and duplicate rows after normalization. Do not imply email ownership is verified. Registration checks the supplied email matches its invitation after normalization. The owner gives the invitation code to the intended person through a known offline channel; the list and code alone do not prove mailbox ownership.

Use a pinned 2,048-word English recovery list with its license and checksum recorded in source. Draw **12 independent uniform word indexes** with a cryptographically secure random generator (132 bits of entropy); this is an app phrase, not a BIP-39 wallet mnemonic. Normalize only case and repeated/leading/trailing whitespace when comparing phrases. Compute `HMAC-SHA-256(RECOVERY_DIGEST_KEY, "recovery-v1|" + normalizedPhrase)` and store only the digest. Version the derivation so Stage 3 can rotate it. Return the plaintext phrase exactly once in the prepare response; neither a status nor a retry endpoint may return it again.

Passwords: accept 12–128 Unicode code points, reject null/control characters and a pinned common-password denylist, and never silently truncate or normalize them. Hash with a per-password salt; compare derived keys in constant time. Store the algorithm, parameters, salt, and derived key in the versioned hash record. A wrong password and an unknown email produce the same public error; run a dummy verification for unknown accounts to reduce timing-based enumeration. Rate-limit before expensive verification.

## API and HTTP contract

All endpoints use `/api/v1`, JSON requests/responses, `Cache-Control: no-store`, typed success `{data:...}`, and typed errors `{error:{code,message,details?}}`, where optional typed `details` may carry `boardRevision`, `allowlistRevision`, or `fieldErrors`. Error messages must be safe to show; clients branch on stable `code`, not translated English server text. Use `400 invalid_request` for malformed data, `401 unauthenticated` for missing/expired sessions, `401 invalid_credentials` for all login failures, `403 forbidden` for role/Origin/CSRF failures, `404 not_found` for unknown resources, `409 conflict` with a more specific stable code for consumed bootstrap/invite, duplicate email, full seats, or stale allowed-list revision, `429 rate_limited` for attempt/queue limits, and `503 unavailable` for transient storage/runtime failure. Do not reveal which credential failed or whether an email is on the allowed list to an unauthenticated caller. The front Worker caps auth JSON bodies at 16 KiB and rejects unsupported content types, but the DO repeats all relevant field validation. Unknown endpoints/methods keep the Stage 1 JSON 404/405 behavior. Do not put codes or phrases in query strings.

| Method and path | Access and request | Success |
| --- | --- | --- |
| `GET /api/v1/auth/bootstrap/status` | Public. No secrets in request. | `{data:{bootstrapAvailable:boolean}}`; false once `app_state.bootstrap_consumed`. |
| `POST /api/v1/auth/bootstrap/prepare` | Public; exact same-origin `Origin`; body `{bootstrapSecret,email,password,language?}`, default language `en`. | `201 {data:{pendingToken,recoveryPhrase,expiresAt}}`. Does not yet create an active owner. |
| `POST /api/v1/auth/registration/prepare` | Public; same-origin `Origin`; body `{inviteCode,email,password,language?}`, default language `en`. | `201 {data:{pendingToken,recoveryPhrase,expiresAt}}`. |
| `POST /api/v1/auth/registration/confirm` | Public; same-origin `Origin`; body `{pendingToken,recoveryPhrase}`. | `201 {data:{user,csrfToken}}` plus a new session cookie. Used for both bootstrap and invitation. |
| `POST /api/v1/auth/login` | Public; same-origin `Origin`; body `{email,password}`. | `200 {data:{user,csrfToken}}` plus a new session cookie. |
| `GET /api/v1/auth/session` | Live session cookie. | `200 {data:{user,csrfToken}}`. No session returns 401; this route never returns a phrase. |
| `POST /api/v1/auth/logout` | Live session cookie, same-origin `Origin`, and CSRF header. | `200 {data:{signedOut:true}}`, revokes this session and clears cookie. A repeated logout with an expired/revoked cookie returns `401 unauthenticated` and clears the cookie. |
| `GET /api/v1/settings/allowed-emails` | Owner session only. | `200 {data:{emails:string[],allowlistRevision:number}}`; sorted normalized emails, including the owner. Never public or member-readable. |
| `PUT /api/v1/settings/allowed-emails` | Owner session, Origin/CSRF; body `{emails:string[],allowlistRevision:number}` is the complete replacement set. | `200 {data:{emails:string[],allowlistRevision:number}}`. A stale revision returns `409 allowlist_conflict` with current `allowlistRevision` in typed error details and no write. |
| `GET /api/v1/invitations` | Owner session. | `{data:{invitations:[{id,email,expiresAt,status}]}}`; never includes codes or digests. |
| `POST /api/v1/invitations` | Owner session, Origin/CSRF; body `{email}`; email must currently be allowed. | `201 {data:{id,email,inviteCode,expiresAt}}`; code appears once, as 32 hex characters (128 random bits). |
| `DELETE /api/v1/invitations/:id` | Owner session, Origin/CSRF. | `200 {data:{revoked:true}}`; marks an unused invite revoked. Already consumed/unknown yields 404 or 409, consistently tested. |
| `GET /api/v1/members` | Any active session. | `{data:{members:[{id,email,role,status,language}]}}`; no credential material. |
| `PATCH /api/v1/members/:id` | Owner session, Origin/CSRF; only body `{status:"inactive"}`. | `200 {data:{member}}`; deactivates a non-owner and revokes every session for that user. Stage 4 adds card-assignment clearing in the same transaction. |

`user` in an auth response contains only `id,email,role,status,language`. The `pendingToken` is 32 random bytes encoded as base64url, expires after 15 minutes, and remains in browser component memory only in Stage 5. The invitation expires seven days after creation. Preparing again for the same invitation or bootstrap invalidates its previous pending registration, but does not consume the invitation. Do scrypt outside SQL, then atomically recheck bootstrap/invitation/email validity and allowlist membership, invalidate earlier pending rows for the same source, and insert the new pending row in one synchronous transaction; in a simultaneous prepare race, only the last committed pending token remains valid. A pending registration can be retried while valid after a mistyped phrase, but five failed phrase confirmations invalidate it; a refresh or expiry requires a new prepare call. The invitation remains unconsumed until successful confirmation. On confirmation, create the user, recovery credential, and session; consume the invitation or bootstrap state; delete the pending record; and enforce seat limits **in one synchronous SQL transaction**. Generate the session token and calculate all hashes before entering the transaction; re-read invitation validity, email uniqueness, pending status, owner state, allowlist membership, and active-seat count *inside* it. Owner bootstrap is exempt from the preexisting-list check but must insert its own email before commit. The caller receives a cookie only after commit.

The `PUT` replaces the entire list atomically, using the same email validation as registration. Require one to seven unique normalized emails, including the current owner's email exactly once, and a nonnegative safe-integer `allowlistRevision`; reject malformed, duplicate, over-limit, or owner-omitting input without changing anything. In one synchronous transaction, recheck the owner's live session/role and `allowlistRevision`, calculate added/removed emails, replace rows, increment the revision once, revoke every session, unused invitation, and pending registration for removed emails, and commit. A no-op replacement may return the current revision without a write. List updates and invitation issue/registration confirmation serialize in this one Durable Object: an invite or activation cannot commit for an email removed first, and a later removal revokes access immediately. An email added back needs a fresh invitation if it has no active account; a previously removed active account may log in again, but still occupies its original seat. Stage 4 extends this transaction to clear affected card assignments and advance the board revision once when eligible active members change, and adds the resulting `boardRevision` to the update response. The API takes an array, while Stage 5 presents one address per line in its textbox; never parse a client-submitted comma list as authorization state.

## Session, CSRF, rate-limit, and authorization rules

Issue a 32-byte random opaque token with 14-day absolute expiry. Store only SHA-256 of the token. Set `__Host-kanban_session=<token>; Secure; HttpOnly; SameSite=Lax; Path=/; Max-Age=1209600` without a `Domain` attribute. Clear with the same cookie attributes on logout. A successful registration confirmation or login always creates a fresh session token. Any **live** session cookie on a pre-auth bootstrap, registration, or login route is rejected with `403 already_authenticated`; the user must sign out with CSRF first. An expired/revoked cookie is treated as absent and replaced only after successful login. Logout revokes its session; deactivation and allowed-list removal revoke all of that member's sessions. Password change and recovery will revoke all sessions in Stage 3. Never put session, phrase, invitation, or pending tokens in `localStorage`, URL, logs, or analytics. All scrypt calls use Stage 1's one-at-a-time bounded KDF queue; a full queue returns a retryable `429` with `Retry-After` rather than starting another memory-heavy hash.

Derive the reissuable CSRF value from the live session: `base64url(HMAC-SHA-256(CSRF_SECRET, "csrf-v1|" + session.id + "|" + session.token_digest))`. Return it in login/confirmation/session responses; require it in `X-CSRF-Token` on every authenticated mutation and compare in constant time. All JSON mutations, including pre-auth prepare/confirm/login, require a present `Origin` exactly equal to the request URL's origin. Browser JavaScript must not try to set `Origin` manually; the browser supplies it, while API test scripts include it explicitly. Do not emit permissive CORS headers. A live session on a pre-auth route is rejected as above; on an authenticated route, missing/forged CSRF is 403. A missing/expired/revoked/inactive/**no-longer-allowed** session is 401, including when a stale cookie survives on another device. Login for a disallowed email returns the same `invalid_credentials` response as a wrong password or unknown account, with a dummy verification path where needed to reduce enumeration. After password verification, recheck both active status and list membership in the same transaction that inserts the new session; a concurrent removal cannot issue a usable cookie. A live member attempting an owner action is 403. Check authorization and allowed-list membership again inside the DO after every asynchronous step and inside every state-changing transaction; hiding the settings UI is never an authorization control.

Persist bounded sliding/fixed-window limits for bootstrap, registration prepare/confirm, and login keyed separately by normalized account email and Cloudflare-provided client IP; HMAC identifiers with `RATE_LIMIT_KEY` before storing. Ignore client-supplied forwarding headers. Start with five failed login attempts per email per 15 minutes and 30 per IP per 15 minutes; five bootstrap attempts per IP per 15 minutes; 10 registration prepare attempts per IP per 15 minutes; and five confirmation failures per pending token. Enforce before scrypt, return `429` with `Retry-After`, and avoid distinguishing unknown accounts by response text. Document how trusted client IP is obtained in production and simulated in tests. Expired rate rows may be deleted without affecting credential state.

Record coarse security events (time, event type, user ID if known, outcome) with no request bodies or secrets. For an allowed-list edit, record the owner ID, revision, and counts changed, not the email rows or full payload. Disable request-body logging, redact cookies and auth headers, and return generic server errors without SQL or stack details. This stage adds safe defaults for auth responses; Stage 7 finalizes the HTML content security policy and broader production header review.

## Acceptance and adversarial review checklist

- The owner can complete bootstrap only with the configured secret and phrase confirmation. A second bootstrap prepare or confirmation fails after activation, even if the secret remains configured. Missing bootstrap secret fails closed. Two simultaneous bootstrap confirmations produce one owner, one failure.
- Bootstrap creates exactly one owner/admin and inserts that normalized email into the allowed list. Only the owner can read or replace the list, through a live session with Origin/CSRF on writes. A member or anonymous caller cannot read it, mutate it, or infer its entries through distinct pre-auth errors. The API rejects malformed/duplicate/over-seven lists and any attempt to remove the owner; a stale `allowlistRevision` rejects without overwriting another edit.
- The owner can issue a seven-day invite and see its code only in the creation response. A valid invited email registers; a mismatched/case-normalized duplicate email, revoked/expired/consumed code, wrong phrase, wrong pending token, or expired pending record cannot activate. Preparing twice, including simultaneous prepares, leaves only the last committed pending token valid. Five wrong phrase confirmations invalidate only that pending registration. An interrupted registration leaves the invitation usable until its own expiry.
- An email not on the allowed list cannot be invited, prepare/confirm registration, log in, or use an existing session, even by calling the API directly. Removing an email during a pending registration revokes its invite and pending record; removing an active member revokes all sessions immediately, including another device's, while preserving the account and occupied seat. Adding that email back restores login only for a still-active account; old invite codes do not revive. Race tests prove removal versus invitation/confirmation/login/board authorization cannot grant access after removal commits.
- The owner plus six members can be active in the isolated test environment. Simultaneous confirmations that would create an eighth produce at most seven active users; the failed invitation remains unconsumed if otherwise valid. Deactivating a member frees one seat, revokes all their sessions, and prevents their login; the owner cannot self-deactivate.
- Password hashes differ for identical passwords due to salt; correct login works; wrong password and unknown email have the same public error. Rate-limit tests show 429 and `Retry-After` before an attacker can force unbounded scrypt work.
- Cookie has `__Host-` prefix, Secure/HttpOnly/SameSite=Lax/Path=/, no Domain, and a bounded expiry. Successful login creates a new token; a live-session attempt to call login/bootstrap/registration is rejected until CSRF-protected logout. Logout invalidates its session server-side. Missing, expired, revoked, or inactive sessions return 401. CSRF token works after page refresh through `GET /auth/session`; wrong/missing CSRF or Origin returns 403. A member calling any owner endpoint returns 403.
- Response bodies, SQL rows, source-controlled files, logs, and test snapshots contain no plaintext password, phrase, invite code after issue, session token, or bootstrap secret. No mail dependency, email-reset endpoint, or credential-bearing URL exists.
- All responses conform to the shared envelope and status contract; the deployed test hostname passes the same security/concurrency suite as local development.

## Exit gate and rollback

Stage 3 may begin when all tests pass on the deployed Free test environment and a disposable owner plus six-member API smoke flow works without leaks, including allowed-list replacement and removal. Stage 4 can use the established user/session tables and shared authorization helper. Stage 4 must extend account activation, deactivation, and allowed-list transactions to increment `board_state.revision` whenever the board snapshot's eligible active-member list changes; deactivation and allowlist removal must clear affected card assignments atomically. Stage 5 builds the one-email-per-row owner settings UI from these exact endpoints. Record any schema/API change centrally and notify dependent stage plans before implementation.

This stage uses only isolated disposable test data. A failed code deploy rolls back to a compatible Worker version that still enforces the allowed list; deploying older auth code without that check would restore access to removed members. A committed SQL migration is **not** reversed by redeploying code; reset the disposable test namespace or apply a tested forward repair. Never use this reset procedure on a live production Durable Object. If test bootstrap is incomplete, expire its pending record and retry; if test owner activation committed, the bootstrap state stays consumed. Stage 7 requires a tested encrypted backup, restore path, and operator runbook before production initialization.
