# Stage 1 — Hosting and Security Feasibility

**Parent:** [Family Kanban Board master plan](../personal-business-goals-dashboard-master-plan.md)  
**Status:** Completed 2026-09-13; [feasibility gate passed](../../docs/stage-1-feasibility.md)  
**Outcome:** One reproducible Cloudflare Free deployment serves the React app and JSON API, persists a test row in a SQLite-backed Durable Object, and proves native scrypt at the required work factor in the deployed runtime.

## Scope and decisions

This stage builds infrastructure and a minimal shell, not accounts or board features. Use a single Cloudflare Worker with Static Assets and one bound SQLite-backed Durable Object. Keep production, test, and restore as distinct Wrangler environments with distinct Durable Object namespaces and fixed object names. Do not deploy an account flow or use real user data yet. Pin the package manager, lockfile, Wrangler version, TypeScript settings, and Worker compatibility date.

Cloudflare's [SPA routing documentation](https://developers.cloudflare.com/workers/static-assets/routing/single-page-application/) explains why navigation requests can otherwise receive `index.html` at API paths. Set `assets.run_worker_first: true` so **all** requests enter the front Worker, and omit `assets.not_found_handling: "single-page-application"`. The Worker explicitly dispatches `/api` and `/api/*` before asset handling. It serves `index.html` only for an allowlist of intended client routes (initially `/`, `/login`, `/register`, `/recover`, and `/board`; later UI routes require an explicit update). All other non-API paths go to `ASSETS.fetch`, which returns 404 for a missing file without SPA fallback. This covers the master plan's API-first and missing-asset requirements without needing a build manifest. Verify browser navigation and ordinary fetch, because asset routing depends on request headers. Cloudflare documents [Worker-first asset binding behavior](https://developers.cloudflare.com/workers/static-assets/binding/) and [default missing-asset handling](https://developers.cloudflare.com/workers/static-assets/).

The front Worker must stay cheap: parse URL, dispatch, bound request bodies, and forward API requests to the fixed Durable Object. The Durable Object owns all SQL access and later authentication decisions. Never let a client-supplied path, query, header, or body select a Durable Object name. Use the same server-fixed object name, `household`, in each environment, but distinct DO namespaces and Worker names; the namespace supplies isolation. Keeping the name stable also makes a later tested namespace transfer possible without changing the object ID derivation. Avoid `PRAGMA user_version`; use an explicit `schema_migrations` table and idempotent versioned migrations. Cloudflare documents [SQLite-backed storage and synchronous transactions](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/) and the current [1 GB per-object Free storage ceiling](https://developers.cloudflare.com/durable-objects/platform/limits/).

## Prerequisites

- A Cloudflare account on Workers Free, permission to deploy a Worker, and local Node.js/npm versions selected and recorded in the repository. Use the included `workers.dev` hostname; do not require a custom domain or paid add-on.
- The master plan's initial scope and source-of-truth contract are accepted. There is no dependency on a mail service, external database, or the saved Hebrew goal prompt.
- Obtain only **test** secrets for diagnostics. Store them in Wrangler secrets, never in source, `wrangler.jsonc`, terminal transcripts, or test snapshots. Production account secrets are provisioned and escrowed in Stage 7 before real owner activation.

`GET /api/v1/health` returns `200` with `{data:{status:"ok",schemaVersion:<integer>}}` and `Cache-Control: no-store`. It does not disclose object IDs, secrets, deployment environment, SQL errors, or user data. An unknown API path returns `404` and `{error:{code:"not_found",message:"Not found"}}` with `Content-Type: application/json`. Wrong methods return `405` with an `Allow` header. The health path may initialize migrations but does not write a probe record on every request.

## Ordered implementation tasks

1. **Record current Free terms.** Recheck [Worker limits](https://developers.cloudflare.com/workers/platform/limits/), [Durable Object limits](https://developers.cloudflare.com/durable-objects/platform/limits/), [Durable Object pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/), and the `workers.dev` route. Record date, relevant quotas, whether excess fails without automatic billing, and the 1 GB Free per-object ceiling. Confirm both the account and intended features are still on the Free plan.
2. **Scaffold and pin the toolchain.** Create the file tree above and a minimal React shell. Choose one testing runner and use Cloudflare's Worker/Durable Object-compatible harness for integration tests. Pin exact package versions in the lockfile and the Worker compatibility date. Build Vite before bundling/deploying the Worker. Ignore `web/dist`, `.wrangler`, local secret files, and generated artifacts.
3. **Configure three isolated environments.** Set distinct Worker names, SQLite DO namespaces/bindings, and secret stores for test, restore, and production; use `idFromName("household")` in each namespace. Declare the distinct production/test/restore class aliases through [Cloudflare's current `exports` configuration](https://developers.cloudflare.com/durable-objects/reference/durable-objects-migrations/) in each environment and pin a Wrangler version that supports it. The restore class name differs from the existing production class name so Stage 7 can transfer it into production as a separate class while retaining the original production namespace. Test/restore routes must not resolve a production stub even if a request supplies a forged object name. Check the generated environment configuration before deployment. Keep restore routes disabled until Stage 7. A namespace cannot be promoted by merely changing a string; Stage 7 must test the documented multi-deploy class-transfer flow.
4. **Implement routing and migration foundation.** Route all requests through the front Worker, then dispatch API paths before assets. For an allowlisted SPA navigation, fetch `/index.html` explicitly; for other non-API paths, fetch the exact requested asset with `ASSETS.fetch` and preserve its 404. Do not configure automatic SPA not-found handling. Add body-size and method checks, JSON errors, and safe exception handling. In the Durable Object, create `schema_migrations` version 1 and a small `diagnostic_probe` SQL table in every environment so schema versions remain identical; only the test environment can write probe rows through the secret-guarded diagnostic route. The probe table is not application data and is excluded from Stage 7 backup. Use supported SQLite APIs and block concurrent startup migration; migration reruns must be no-ops. Verify build output and SPA route allowlist.
5. **Prove SQL on the actual Free deployment.** Deploy the test environment to its `workers.dev` hostname. A temporary, secret-guarded test diagnostic writes a nonce, reads it on a later request, and removes it. Verify persistence after a new Worker/DO session. Remove or compile out the diagnostic handler before production deploy; never leave public SQL-write or benchmark routes.
6. **Prove password hashing on the actual Free deployment.** In the test DO, call supported native `node:crypto` scrypt at `N=2^14,r=8,p=5` with a fresh 16-byte-or-longer salt and a 32-byte derived key; hash and verify, including an incorrect password. Use the bounded single-operation KDF queue so seven simultaneous calls do not allocate seven memory buffers at once. Run at least 20 timed warm and cold attempts and a seven-request burst. Measure p50/p95 latency, CPU duration, failures/timeouts, queue wait, and peak memory where observable. **Pass only if** p95 is under 5 seconds for one operation, the seven-request burst completes within 15 seconds without timeout, the parameters are not weakened, and there is no runtime CPU or memory failure. Cloudflare documents [`node:crypto` support](https://developers.cloudflare.com/workers/runtime-apis/nodejs/crypto/) and [30-second default DO CPU per request](https://developers.cloudflare.com/durable-objects/platform/limits/); [OWASP's password storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) supplies the work-factor baseline.
7. **Verify and document deployment.** Run lint, typecheck, build, and tests; optionally deploy an empty production shell only after diagnostics are absent and test proof passes. No real owner or account data is created before Stage 7 has backup and restore procedures. Record exact commands, measured values, `workers.dev` URLs, quota state, and a reproducible clean-checkout deployment procedure. Stage 2 must read this feasibility report before implementing accounts.

## Acceptance and adversarial tests

- `/`, `/login`, and `/board` serve the shell on direct navigation; existing JS/CSS assets serve their actual MIME types. A missing `/assets/not-found.js`, nested missing `/assets/x/y.png`, `/foo.png`, unknown `/arbitrary`, `/api`, `/api/unknown`, and `/api/v1/unknown` never return the SPA HTML. Test both `Sec-Fetch-Mode: navigate` and normal fetch. A missing API returns JSON 404.
- `GET /api/v1/health` works locally and at the deployed test host, and at the production host if the optional empty shell was deployed. A wrong method is 405. A malformed request never leaks a stack trace or secret.
- SQL writes survive later requests and DO restart in test. Migration rerun preserves the probe row and applies no duplicate tables. The test and restore object IDs/namespaces are demonstrably distinct from production.
- Hash verification succeeds for the correct password and fails for a wrong one; two salts yield different hashes. Benchmarks run inside the deployed **Free DO**, not merely Node or local Wrangler. A seven-call burst remains bounded in memory; when one operation runs and seven others wait, a ninth caller gets a controlled retryable error rather than starting another hash. Diagnostic routes reject missing/wrong secret during the test and are absent from production.
- A test request attempting to override the object name does not touch another environment. Source, build output, and logs contain no diagnostic secret or password.

## Exit gate and rollback

Stage 2 starts only after a repeatable clean deployment, routing and SQL tests, a dated Free-tier quota record, and a recorded passing scrypt benchmark. If native scrypt, the configured work factor, or the Free runtime fails even with bounded concurrency, **stop** and revise the master hosting decision before storing credentials; do not lower the work factor to make the test pass.

Rollback of this stage is safe because it contains no real accounts: redeploy the prior Worker version or delete the test Worker and its test DO namespace after preserving the feasibility report. Do not delete the production DO namespace after real owner initialization in Stage 7. Future production schema migrations require a backup and explicit rollback/restore procedure in Stage 7.
