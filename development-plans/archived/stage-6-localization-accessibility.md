# Stage 6 — Localization and Accessibility

**Status:** Ready to implement after Stage 5; translation drafting can start after UI keys are defined  
**Status:** Closed by owner decision on 2026-09-13, without the manual screen-reader review this plan's exit gate calls for. See the [Stage 6 completion report](../../docs/stage-6-completion.md).  
**Scope authority:** [`personal-business-goals-dashboard-master-plan.md`](../personal-business-goals-dashboard-master-plan.md)  
**Deliverable:** Complete English, Hebrew, and Russian workflows with correct direction, keyboard access, and assistive-technology feedback.

## Scope and prerequisites

Stage 5 must expose all user-visible copy through typed translation keys and provide the account and board workflows. Stage 2 provides the `users.language` field, defaulting to `en`, and includes it in session reads. Stage 6 owns the authenticated language-update route and UI persistence. Keep English as the fallback only for development; the release build must fail when any language is missing a key. The application remains one board for up to seven people. This stage changes presentation and a small preference operation, not the card schema or authentication rules.

## Concrete contracts and files

Use three UTF-8 dictionaries such as `web/src/i18n/en.ts`, `he.ts`, and `ru.ts`, generated or checked against one typed key set. A `web/src/i18n/index.ts` locale provider exposes `t(key, params)`, current locale, and `setLocale`. Store only the allowlisted locale values `en`, `he`, and `ru`. On first guest visit, choose a non-sensitive locale cookie if present, otherwise `navigator.languages` (Hebrew variants to `he`, Russian variants to `ru`, else `en`). Initialize `<html lang/dir>` before React renders to avoid a wrong-direction flash. A guest switch updates the cookie and screen immediately; `bootstrap/prepare` and `registration/prepare` persist that chosen locale for the new account. After sign-in, the persisted user preference takes precedence and a switch calls the authenticated preference API; update the guest cookie on successful persistence so sign-out keeps the selected language. On failure, show a save failure and revert to the last server-confirmed preference and cookie. Locale preference never lives in an auth token.

Stage 2's `users.language` is `TEXT NOT NULL DEFAULT 'en' CHECK (language IN ('en','he','ru'))`, and `GET /api/v1/auth/session` returns `user.language`. Stage 6 adds `PATCH /api/v1/me/preferences` with body `{ "language": "en" | "he" | "ru" }` and success `{data:{language}}`. Implement it in `worker/src/routes/` and the bound Durable Object. It requires a live session, exact same-origin `Origin`, and `X-CSRF-Token`, validates the enum, and updates only the current user's record. Return Stage 2's `{error:{code,message}}` shape on failure. Do not permit one user to edit another's language.

Set `document.documentElement.lang` and `.dir` synchronously on locale changes: `he` maps to `rtl`, `en` and `ru` to `ltr`. Apply `dir="auto"` to user-authored card title/description and custom column names. Keep email addresses, the owner's one-email-per-row allowed-list textbox, invitation codes, recovery words, token entry, and technical identifiers in isolated LTR spans or inputs, including within RTL sentences. Prefer CSS logical properties (`margin-inline`, `padding-inline`, `inset-inline`, `border-inline`) and direction-aware flex/grid behavior. Mirror only semantic directional icons and movement arrows, not logos, text, or arbitrary glyphs. The server stores and returns user content verbatim; translations do not rewrite data.

## Ordered work

1. **Translation inventory.** Enumerate every visible string and accessible name in guest routes, invitation/registration, phrase confirmation, login/logout, account settings (including allowed-email editing, removal/seat warnings, and stale-list conflicts), self-service and operator-token recovery, owner member and column controls, board/card dialogs, errors, conflict notices, empty/loading states, confirmations, help text, move controls, and rate-limit feedback. Use stable keys with interpolation for counts and names; avoid concatenating sentence fragments. Include plural forms where each language requires them.
2. **Complete dictionaries and validation.** Write natural English, Hebrew, and Russian copy. Preserve the meaning that no email is sent, the phrase is displayed once, and a lost phrase requires offline owner contact. Review the UI in context, not just dictionary files. Add a build/CI check that compares key sets, interpolation parameters, and unsupported locale values; no missing key may silently render English in the release build. Do not translate user-supplied card/column content.
3. **Preference and direction.** Implement guest detection/cookie and authenticated persistence using the contract above. Switch text and `<html lang/dir>` immediately without reloading, and restore a saved preference on a new session/device. Ensure the guest language selector remains available before registration and during recovery. Apply logical CSS to layouts, dialog placement, board scrolling, icon placement, and form validation; inspect every route at desktop and mobile widths.
4. **Bidirectional-content checks.** Render mixed Hebrew/English/Russian names and card text, Latin email addresses, passwords, invitation codes, and recovery words in each page direction. Keep codes selectable/copyable and in the correct character order. Verify card order and drag destinations remain semantically correct when the visual direction reverses; column navigation and explicit move labels must describe the actual resulting order.
5. **Keyboard and screen-reader behavior.** Ensure every operation can be completed without a pointer: sign-in, phrase confirmation, all dialogs, board navigation, card create/edit/assign/delete, owner controls, keyboard drag, and explicit move actions. Provide visible focus and sensible tab order. After dialogs, return focus to a valid triggering control or its stable successor. Announce move success, rejected/conflicted move, save errors, card deletion, and loading completion through a polite or assertive live region as appropriate; avoid duplicate announcements from the drag library. Label fields, errors, buttons, columns, cards, and drag instructions in the active language.
6. **Visual accessibility.** Check contrast for text, controls, focus rings, and error states; do not rely on color alone. Test at 200% zoom, reduced motion, mobile widths, and touch targets. Preserve legibility and access to all column/card actions while the board scrolls horizontally. Use semantic headings, landmarks, list/region relationships, and dialog roles where applicable.
7. **Localization quality review.** Run workflows in each locale against disposable accounts in the isolated Free test environment, including real server validation failures, `401`, `403`, `409`, `429`, offline/retry states, and pending phrase flows. Review translation length, clipping, bidi punctuation, and announcements. Document any deliberately untranslated product name or user-generated text. Do not initialize the real production household before Stage 7.

## Acceptance tests

- In English, Hebrew, and Russian, an invited member can register, save/confirm a phrase, sign in, move/edit/assign a card, reset a password with the phrase, and sign out. The owner can invite, deactivate, and manage columns. The manual-token recovery screen is localized too.
- Switching to Hebrew sets `lang="he" dir="rtl"` immediately; switching to English or Russian sets `ltr`. A signed-in selection persists after a fresh login; a guest choice persists without storing a credential. A failed preference save is visible and does not falsely appear persisted.
- A release dictionary check reports zero missing, extra, or parameter-mismatched keys; visible validation and API errors are localized. User-authored text stays unchanged.
- Mixed-script card titles/descriptions, custom column names, email, invite/reset codes, and recovery words display in a readable order in both directions. Copying a code yields exactly the original bytes/characters.
- Keyboard-only users can perform every card and account action, including reordering without drag. Focus never becomes trapped behind a dialog or lost after a move/delete. A screen reader announces move success and conflict once, in the selected language.
- At 320 CSS pixels, 200% zoom, and common mobile widths, text and controls are reachable and not clipped. Focus indicators and contrast pass the project's accessibility audit. Reduced-motion users do not require animations to understand state changes.
- E2E locale smoke tests and automated accessibility checks pass; manual screen-reader review covers at least one representative desktop and one mobile workflow in all three locales, with findings recorded and fixed before release.

## Delivery and exit gate

Deliver complete dictionaries, typed key validation, locale preference persistence, direction-aware styling, accessible movement/focus/announcements, and a compact QA matrix recording device, locale, direction, keyboard, screen-reader, and mixed-script results. Stage 6 is complete when registration, recovery, and board workflows pass in every locale at desktop and mobile widths with no missing release translations or inaccessible essential action.

## Rollback

The Stage 2 `users.language` field remains in place; Stage 6 adds only its preference-update route and UI. If a locale or direction change breaks core workflows, roll back the UI bundle to the last version with complete working dictionaries while leaving persisted preferences intact. If only a translation is wrong, patch the dictionary and redeploy the static bundle. Do not silently force all users to English or discard saved preferences.
